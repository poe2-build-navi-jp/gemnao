# 非公開診断受付：まとめて確認する公開前作業

**現時点はコード候補のみ。受付・管理閲覧は既定OFFです。** 本番DB、認証、権限、cron、公開設定は変更していません。以下は実施許可を求めるための具体的な範囲であり、このPRで実行済みではありません。

1. **運営者の認証を確認**：既存管理ログイン `https://gemnao.pages.dev/admin/discord-servers` の「管理キー」欄を使います（お問い合わせ管理にも同じログインフォームがあります）。これはDiscordアカウントのOAuthログインではありません。共通キーはDiscord掲載審査、お問い合わせ、ゲーム追加要望、検索需要集計、コミュニティ投稿と受付制御・検証、および限定診断QAの認証にも使われます。設定名は `DISCORD_ADMIN_TOKEN_HASH` / `DISCORD_ADMIN_TOKEN`、Cookie名は `gemnao_discord_admin` です。既存管理キーを運営者だけが保持するかを本人が確認してください。キーの値をチャットへ貼る必要はありません。共有キーなら、運営者だけの権限を分離する設計・承認が必要です。未確認のまま閲覧スイッチを有効にしません。新しいキーや権限は勝手に作りません。
2. **隔離した試験DB・実行環境の承認**：専用 `PRIVATE_DIAGNOSTIC_DB` を新設する範囲、容量・費用・利用可能な既存権限を確定。既存の投稿・共有・お問い合わせDBへ接続しません。`migrations/private-diagnostic/0001.sql` だけを確認済み試験対象へ適用する承認が必要です。現行preview設定はDBなしのままです。
3. **削除と監視の承認**：同じ専用DBに結び付くcleanup Workerの配備、毎時実行、失敗／2時間超のheartbeat遅延の通知先を承認・設定。架空データで期限切れ削除と通知到達を実証。アプリ側の30日保持と事業者のバックアップ／ログ保持は別です。cronが止まると新規受付を止め、本人の削除は維持します。
4. **分離環境での最終QA**：本人同意・内容変更時の解除、既存管理ログインと未認証拒否、同じ受付番号の再試行、通信断、保存失敗、削除後の再送、1000保持行の上限、停止中の削除を実環境で確認。実データをテストに使いません。公開コミュニティに表示されないことを確認します。
5. **Windows実機確認**：承認済み標準ユーザーのWindowsでJA/ENの専用JSONプレビュー・保存・ブラウザを開く確認、ファイル選択、同意OFF、送信、受付情報保存・再読込・削除を試験環境で確認。DPAPI履歴など既存回帰項目も継続。接続可能なWindowsがない現在は全て未実施です。保護機能回避・管理者実行で通しません。
6. **本番への承認を別途受ける**：本番専用DBへの移行、binding、cleanupと監視、本番コード配備、既存管理キーの運営者限定確認をそれぞれ記録してから、`PRIVATE_DIAGNOSTIC_OWNER_REVIEW_ENABLED=true` と `PRIVATE_DIAGNOSTIC_ENABLED=true` を明示設定します。先に受付だけを有効にしません。実機未検証のバイナリを既定ダウンロードへ昇格しません。

## 停止・戻し方

新規受付停止は `PRIVATE_DIAGNOSTIC_ENABLED=false`。専用DB・削除API・cleanupを残して、本人の削除と保持期限を維持します。管理閲覧停止は別スイッチです。binding削除・Worker削除・DB削除・キー変更は別の承認と保持／削除継続計画が必要です。既存の500受付枠や他機能の設定は触りません。

## 利用者の操作

候補アプリの「4 詳細と保存」→「非公開受付用JSONを確認・保存」→全文確認→ローカル保存（ここでは送信しない）→Web受付を開く→JSON選択→全内容と保持期限を確認→同意をチェック→明示送信。成功表示と受付番号を確認し、削除・再試行用の受付情報を手元に保存します。結果不明時は新しく送らず、同じ受付情報を読み込んで再試行します。受付停止中は送れません。運営者の返信・解決や完全匿名性は保証しません。
